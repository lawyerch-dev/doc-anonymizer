# Architecture and Directory Design

For **how to use it**, see [README](../README.en.md); for **boundaries that must not be violated**, see [AGENTS.md](../AGENTS.md).
This document explains "why the packages are split this way and the directories are laid out this way", and records the motivation behind each relocation.

## 1. The Five-Package Structure

```
packages/
├── docanon-contract/          the only shared layer between engines and the app: Block/Span/Detection/Engine ABC
│                              (standard library only, zero runtime dependencies)
├── docanon-engine-ocr/        OCR engine: RapidOCR wrapper + image/scanned-page extraction (→ text + bbox)
├── docanon-engine-ner-onnx/   ONNX NER engine: encoder-style Chinese NER (the label→entity-type vocabulary is supplied by the app)
├── docanon-engine-ner-llm/    LLM NER engine: llama-server (OpenAI-compatible) transport layer + detector
└── docanon-core/              app: extraction/detection orchestration, redaction and write-back, ledger, CLI, local Web
```

Under `packages/` there is also `ui` (the shared JS component library); it is not one of these five Python packages and does not participate in this dependency direction.

The dependency direction is a one-way street, **locked down jointly by the packages and pyproject** (`tests/test_architecture.py`):

```
core ──► engine-ocr ──┐
     ├─► engine-ner-onnx ──┼──► contract
     └─► engine-ner-llm ───┘
```

- Engine packages **do not depend on one another**; each depends only on the contract. Moving one out wholesale = copying "the contract + that one engine package"
  (`tests/test_engine_portability.py` really copies it elsewhere and imports it, with the other two packages planted as traps that throw).
- core may only use engine packages' **public surface** (`from docanon_engine_x import Y`); it must not reach into internal modules such as `...detector`.
- Dependency ownership follows the implementation: `numpy`/`tokenizers` belong to the ONNX engine, `rapidocr`/`onnxruntime`/`Pillow` belong to the OCR engine,
  and `pyyaml`/`pypdfium2`/`python-docx`/`openpyxl`/`Pillow` belong to core (write-back needs them).
  They used to be mixed together in a single `[ocr]` extra, and there were even implicit dependencies (numpy/tokenizers came in incidentally via rapidocr).

### Inside core: Layering by Pipeline

```
docanon_core/
├── cli.py inventory.py          entry point / `docanon engines` self-check manifest
├── config.py resources.py       configuration and resource root (the LAYOUT layout table is the single source of truth)
├── extractors/                  extraction layer: base (routes by extension) text_file pdf table
├── detectors/                   detection layer: base (DETECTORS registry) rule dictionary
├── redaction/                   replacement and write-back: strategies mapping resolve writers
├── pipeline.py job.py           orchestration / ledger (manifest+mapping, atomic writes)
└── server/                      local Web: routes (answers requests) lifecycle (sidecar self-termination)
```

## 2. Repository Root (Why Only These Remain)

```
doc-anonymizer/
├── packages/
│   ├── docanon-*        five Python packages (see above); each package ships its own tests/
│   └── ui/              shared component package @doc-anonymizer/ui: velora components + design tokens (imported by both the website and the product frontend)
├── apps/
│   ├── web/             product frontend (Vite+React): src/ sources → dist/ artifacts, docanon web serves dist/
│   └── desktop/         Electrobun shell (system WebView) + hutch.lock
├── configs/             runtime configuration (default / onnx / llm) —— travels with the resource root, not part of any package
├── samples/             built-in samples: Web presets + test data (generated by scripts/make_samples.py)
├── scripts/             developer scripts (see scripts/README.md)
├── tests/               cross-package tests: package boundaries + portability + e2e/webkit
├── website/             website + docs site: Astro 5 + Starlight, static output to dist/
├── .agent/              categorized conventions for agents: AGENTS.md is the index, rules/ holds the details
├── docs/                this document / benchmarks.md / specs/ (design history)
├── var/                 local reproducible state (gitignored): models weights / vendor preview bundles / out default artifacts / pycache bytecode
├── package.json         frontend workspace root + **the single command entry point** (npm run setup/dev/test/build/...)
├── package-lock.json    frontend dependency lock (reproducible installs)
├── pyproject.toml       Python-side workspace root: pytest configuration only (there is no package here, and no code)
├── requirements-dev.txt one command installs all five packages (editable) + test dependencies
├── conftest.py          shared fixtures (repository root, usable by every package's tests)
└── open-source project facade  LICENSE / CHANGELOG.md / CONTRIBUTING.md / .gitattributes
                          .github/ contains: SECURITY.md / CODE_OF_CONDUCT.md / issue and PR templates
```

`configs/` and `samples/` are deliberately left at the repository root instead of being stuffed into a package: they are the contents of the **resource root**
(moved separately from the code when packaging the desktop app), and their paths are all managed by one table, `resources.LAYOUT`. Default artifacts also land in `var/out`,
so "running the tool once" leaves no junk at the root.

## 3. Development and Testing Do Not Require Launching the Desktop Shell

Day to day it is just `npm run setup|dev|test` (for what the commands mean, see [README](../README.en.md)).
The shell merely puts the same Web UI into a native window, and rendering inside the shell is covered by `tests/e2e/webkit/` (Playwright's WebKit engine),
so changing the UI does not require opening a window.

## 4. Six Hard Boundaries (All Locked by Tests; Do Not Bypass)

| Boundary | Where it is locked | Consequence of violation |
|---|---|---|
| Contract is standard library only; engines depend only on the contract + themselves; core uses only the engines' public surface; pyproject dependencies match the code | `tests/test_architecture.py` | Package boundaries rot and "moving a package out wholesale" no longer holds |
| An engine can be moved out wholesale | `tests/test_engine_portability.py` (copied into an environment with only the contract + itself, then imported) | An engine secretly depends on core and explodes the moment it is moved |
| The resource root is verifiable and the layout has a single source of truth | `packages/docanon-core/tests/test_{resources,layout}.py` | Under a non-editable install it silently reads an empty configuration |
| Artifact naming `【脱敏版】<full name>[.<target extension>]` + subdirectories preserved; deterministically truncated beyond 255 bytes (extension kept + `~` short hash); the ledger is written atomically per file, and `--resume` requires the artifact to still exist | `test_output_layout.py`, `test_job.py` | Same-name overwrites; a crash loses records; a missed redaction is reported as already handled |
| A PDF hit page retains no extractable text (non-hit pages are preserved as-is) | `test_pdf_output.py` ([decision record](../.agent/notes/implemented/architecture/2026-10-06-pdf-hit-pages-rasterized.md)) | Painting a black box over the text layer = the original is still copyable = not redacted |
| **Docs do not drift from code** (paths, links, test file names, the test count in AGENTS) | `tests/test_docs.py` | The code moved but the docs still describe the old layout — self-contradictory, and readers are led into a ditch |

Common principle: **"rather error out than silently skip a layer"** (`prepare_detectors` pre-check, `ResourceRootError`,
`load_config` throws when it cannot read, the three-state `manifest`, `LLMError`, PDF rasterization).

## 5. Key Decision Records (This Project's ADRs)

This section *is* this project's architecture decision record: every entry states its **rationale** and its **cost**, and also covers rejected options.
It deliberately does **not** open a separate docs/decisions/ directory — one decision with two sources of truth will eventually contradict itself
(this kind of drift cannot be caught by `tests/test_docs.py`, only avoided by "exactly one source of truth").

| Decision | Rationale | Cost |
|---|---|---|
| **Split into five packages** (contract + core + 3 engines) | Dependency direction and "movability" are expressed by the package system, which is harder than "directories within the same package + test constraints"; each package's dependencies are exactly what its implementation needs | Installation needs one more step, `requirements-dev.txt`; cross-package refactors must edit pyproject |
| Engines split into three instead of one | OCR / ONNX NER / LLM NER have completely different dependencies and failure modes (one eats rapidocr, one eats onnxruntime, one is just HTTP); once separated, each can be installed and tested on its own | More packages |
| Do not use entry points to discover engines | Discovery failure is inherently a silent downgrade, which conflicts with "a missing layer must error"; core imports the three engines explicitly and registers them explicitly in the registry | Adding an engine requires editing core's pyproject and the registry (intentional) |
| Default artifacts land in `var/out` | Running the tool once leaves no junk at the repository root; a single gitignore entry for `var/` covers it | Differs from `-o out` in older docs and in muscle memory |
| `configs/` `samples/` stay at the root, not in a package | They are the resource root's contents, moved separately from the code when packaging; `resources.LAYOUT` manages them uniformly | Requires the concepts of a resource root and `DOCANON_ROOT` |
| **No self-contained wheel** | The frontend vendor is 232MB and the models are GB-scale; they should not go into the package | `pip install .` elsewhere is unusable (explicit error + `DOCANON_ROOT`) |
| **Frontend moves to Vite + React + TS** (node at build time, zero node at runtime; decision details: [note](../.agent/notes/implemented/architecture/2026-10-09-product-frontend-on-vite.md)) | Reuses `packages/ui` (changing stacks does not change the look) and gains real type checking plus bundling/minification | One more build chain and a dist prerequisite |
| Rasterize PDF hit pages in full | A black box does not change the content stream; the original remains copyable/searchable | Hit pages are no longer editable (already narrowed to "only the pages that hit") |
| Command entry = the repository root's npm scripts (`scripts/dev.sh` demoted to the implementation layer) | The frontend already needs node anyway: a one-shot `npm run dev` / `npm test` is easier to remember than `./scripts/dev.sh <subcommand>`; shell logic stays in dev.sh, not stuffed into package.json | One extra wrapper layer (troubleshooting can still use dev.sh and the underlying commands directly) |
| Development docs: `AGENTS.md` is only an index, details split into `.agent/rules/` | A 160-line "everything crammed in" file that nobody reads to the end before acting; once split by topic, changing the frontend means reading only the frontend article | One more hop in the docs; guarded against bloat (AGENTS ≤80 lines, each article ≤60 lines, every article indexed) |
| Frontend components extracted into a shared package `packages/ui`; the website uses Astro + Starlight (decision details: [shared package](../.agent/notes/implemented/architecture/2026-10-07-shared-ui-package.md) · [Astro choice](../.agent/notes/implemented/architecture/2026-10-07-astro-starlight-for-website.md)) | velora (MIT shadcn components) is React/Tailwind 4; components and tokens live in exactly one place, and `website/` and the product frontend (`apps/web`) import the same package — **reuse via a package, not via copy**. Starlight was chosen for the website because search/TOC/prev-next/i18n are built in, and its 241MB of dependencies and 0.7s build are an order of magnitude smaller than the Next-based option (measured comparison in website/README.md) | The frontend gains npm workspaces and a build chain (build-time only); the website and the product app use two different frameworks (components remain shared) |
| Desktop shell uses Electrobun | System WebView, an order of magnitude smaller | You wade through WKWebView's pitfalls yourself (Tauri died on PDF jitter) |

## 7. Three Things Deliberately Not Done (Not Debt, but Reasoned Choices)

| Not done | Rationale | Evidence/fallback |
|---|---|---|
| Publish engines to a package index and let third parties plug in via entry points | There are no third-party consumers; discovery failure is a silent downgrade, which conflicts with "a missing layer must error". **The packages are already standalone**; all that is missing is "publishing" | `tests/test_engine_portability.py` proves a single engine package can be taken away independently |
| Introduce lint / typecheck / CI | A single-person local tool with no remote; tests are the gate. Actually adding lint would also overturn the convention in `AGENTS.md` to "not add things on the side" | The full test suite covers package boundaries/portability/layout/artifacts/service lifecycle/browser side |
| Make PDF artifacts "selectable/editable" | Keeping the text layer means the sensitive original can still be copied/searched — that is a leak, not a feature | Hit pages rasterized + non-hit pages preserved, locked down by `test_pdf_output.py` |
